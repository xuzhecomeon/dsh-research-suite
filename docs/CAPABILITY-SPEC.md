# 能力融合规范（CAPABILITY SPEC）v2.0.0

本文件是 dsh-research-suite v2 的**唯一内容契约**。任何写入 `data/capabilities/*.json` 与 `skills/research-*.md` 的产出都必须符合本规范。

---

## 一、为什么不是"技能路由"，而是"能力融合"

v1 的做法是给每个任务一个"首选技能"（`primary`）+ 几个"备选"（`backup`），再让模型去读那个技能的原文照做。问题有三：

1. **机械单选违背事实**：同一功能常有 3～8 个技能，各有各的长处。以中文润色为例，"去文言化"最强的是 A，"字数守恒"最严的是 B，"Word 精修报告"只有 C 会做。单选任何一个都必然丢掉另外两个的长处。
2. **选中≠会用**：技能原文是给"人读的说明书"，动辄 8～25 KB，模型照读会遗漏判据、阈值、模板；而且不同技能的术语、步骤顺序互相冲突。
3. **责任不清**：模型拿到一串技能名，等于把"怎么组合"的难题又踢回给它。

v2 的答案是引入中间层——**能力卡（capability）**：

> 一个能力 = 一件可独立验收的事（"给中文稿去 AI 味并保持字数"、"做倾向评分匹配并出 Love plot"）。
> 每个能力卡把**所有**竞争技能拆成 `best_at / limits / take` 三元组，再合成为一条**融合协议（protocol）**。
> 模型不需要选技能，只需要选能力，然后照协议执行；协议里明确写了每一步"取自谁、为什么取它、放弃了谁、为什么放弃"。

**判据**：读完一张能力卡，读者应当能在**不打开任何原始 SKILL.md** 的情况下完成这件事。原始原文作为 `kb` 深读层保留，是"查细节"用的，不是"照做"用的。

## 二、产出物与写面（每个域三件套）

| 文件 | 作用 | 长度基线 |
|---|---|---|
| `data/capabilities/<domain>.json` | 机器可读：能力清单 + 成员对比 + 协议 + 判据 + 门禁 | 每能力 1.5～4 KB |
| `skills/research-<domain>.md` | 模型可读：该域的融合 SOP，含真实可执行细节（模板、阈值、脚本片段） | 18～35 KB |
| `data/capabilities/<domain>.notes.md`（可选） | 挖掘记录：哪些技能被合并/淘汰、为什么 | ≤ 4 KB |

**不要**改 `data/capabilities/*.json` 以外的任何文件（`index.js`、`lib/`、`package.json`、其它域的文件都属他人写面）。

## 三、`data/capabilities/<domain>.json` 结构

```json
{
  "domain": "polish",
  "label": "润色与去 AI 味",
  "skill": "research-polish",
  "version": "2.0.0",
  "summary": "该域解决什么问题、边界在哪（2～4 句）",
  "capabilities": [
    {
      "id": "polish.deai",
      "label": "中文去 AI 味与学术润色",
      "summary": "一句话：接什么输入、交什么输出",
      "triggers": ["润色", "去AI味", "降AI率", "学术化改写", "改得像人写的"],
      "inputs": ["中文稿（docx/md）", "目标期刊或范本"],
      "members": [
        {
          "skill": "paper-deweight",
          "verdict": "主用",
          "best_at": ["文言/半文半白腔调识别与还原", "字数守恒（±5%）"],
          "limits": ["只改语言不改结构", "对英文稿无意义"],
          "take": ["第三人称学术书面语替换规则", "文言虚词黑名单", "字数守恒校验流程"]
        }
      ],
      "protocol": [
        {
          "step": "1 立标杆（不立标杆不动笔）",
          "from": "paper-deweight#以标杆为参照 + wb-academic-polish#选刊定位",
          "do": "先取 2～3 篇目标期刊近三年同型范文，抽取句长分布、连接词密度、段落首句句式，形成一份 10 行以内的"语体指纹"。",
          "detail": "语体指纹至少含：平均句长、每段句数、第一人称出现次数、"显著/提示/表明"类动词偏好、被动句比例。没有指纹就改稿＝凭感觉改，必然来回拉锯。"
        }
      ],
      "decide": [
        {
          "when": "用户明确要 Word 精修报告（逐句修改说明）",
          "use": "paper-polisher 的批注式报告",
          "instead_of": "paper-deweight 直接在正文改",
          "why": "前者留痕可复核，后者快但不可追溯"
        }
      ],
      "gates": ["字数变动 ≤ ±5%", "未改动任何专业术语/剂量/数值", "文言虚词命中数为 0", "全角标点校验通过"],
      "outputs": [".docx 修改稿", "修改说明表（原句/改句/理由/依据）"],
      "kb": ["paper-deweight", "paper-polisher", "humanizer-zh"]
    }
  ]
}
```

### 3.1 字段硬约束（违反即校验失败）

- `id`：`^[a-z][a-z0-9]*\.[a-z0-9-]+$`，全局唯一，形如 `stats.psm`。
- `triggers`：3～10 条，必须是**用户可能原话说出来的中文短语**，不是术语堆砌。用于给 `research_playbook` 做匹配，所以要覆盖口语变体（"降重""不像 AI 写的""帮我润润"）。
- `members`：**2～6 个**。少于 2 说明没融合可言（直接写成通用步骤即可）；多于 6 说明聚类没做完。
  - `skill` 必须是 `knowledge/catalog.json` 里**真实存在**的 name（校验脚本会对账；禁止编造）。
  - `verdict ∈ {主用, 补强, 兜底, 弃用}`。`弃用` 也必须写清 `limits` 与为什么不用。
  - `best_at` / `limits` / `take` 各 ≥1 条，每条 8～40 字，必须是**可验证的具体差异**，不许写"效果好""更专业"。
  - `take` = 实际搬进 protocol 的那部分（规则/表/阈值/模板/脚本）。这是"取长补短"的账本：protocol 里用到的每个外来招法，都必须能在某个 `take` 里找到出处。
- `protocol`：3～8 步。每步必须有 `do`（做什么，可执行）与 `detail`（怎么做，含阈值/模板/判断标准，≥40 字）。`from` 写明来源技能（`技能名` 或 `技能名#该技能里的哪一节`）。
- `decide`：0～4 条**真正的分歧点**（两条技能路线都可行时怎么选）。没有分歧就不要硬凑。
- `gates`：≥2 条，**可机械检查**（数字/文件/一次命令能验），不许写"质量要高"。
- `outputs`：≥1 条，落到具体文件格式（`.docx` / `.csv` / `图 300 DPI PNG` / `xlsx`）。
- `kb`：1～4 个技能名，供 `research_kb_read` 深读。

## 四、`skills/research-<domain>.md` 结构

frontmatter：
```yaml
---
name: research-polish
description: |
  一句话（≤120 字）：本域覆盖什么、什么时候必须用它。会进系统提示的技能目录，务必带真实触发词。
whenToUse: 出现"润色/去AI味/降重/审校"等诉求时。
---
```

正文固定七节（顺序不可变）：

1. `## 一、本域边界`——做什么、不做什么、什么时候转其它域（3～6 条）。
2. `## 二、融合对比表`——一张 Markdown 表：`能力 | 主用技能 | 关键长处 | 明确短板 | 融合取舍`。这是"取长补短"的人类可读账本。
3. `## 三、融合协议`——按能力分小节，每小节按 `protocol` 展开为可执行步骤（编号、动词开头、含阈值与判断标准）。
4. `## 四、判据与红线`——`decide` + `gates` 展开，写成"若…则…否则…"。
5. `## 五、模板与校验`——真实可用的模板：检查清单、替换表、脚本片段（R/Python 要能直接跑）、报告格式。
6. `## 六、交付物`——文件名、格式、目录约定。
7. `## 七、来源索引`——`kb` 技能名 → `knowledge/skills/<domain>/<slug>.md` 的相对路径，供深读。

**细则**：
- 中文全角标点；术语中英对照首次出现时给出。
- 禁止"可参考某某技能"这类空话——要么写清该技能的具体招法，要么不提。
- 涉及脚本的，写清解释器绝对路径与调用注意（R 要清 `LC_ALL/LANG/LANGUAGE`；R 脚本必须 UTF-8 无 BOM）。**但不要把某台机器的绝对路径写死进"必须"语境**——写成"若本机有 R，取 `Rscript`；否则如实告知并给出手工步骤"。
- 每个数字（阈值、EPV、DPI、字数）都要有出处或理由，不许拍脑袋。
- 不要在正文里重复 JSON 的 `members` 原文，要**展开成判断力**（什么时候该用谁的那一招）。

## 五、挖掘流程（照做，别跳步）

1. **读目录**：`knowledge/catalog.json` 里筛 `domain` 为本域的条目，得到 `name / description / bytes`。
2. **聚类**：按"用户要做的事"分组（不是按技能名分组）。一组 = 一个潜在能力。判据：这组技能能否被同一句用户诉求触发。
3. **深读竞争者**：对每个簇，选 2～6 个代表（优先：description 提到具体方法/阈值/模板的、字节数大的、名字直指的），用 read 工具**完整读** `knowledge/skills/<domain>/<slug>.md`。读的时候只回答四个问题：
   - 它最擅长的那一招是什么？（`best_at`）
   - 它明确不做什么/不适合什么？（`limits`）
   - 这一招怎么搬进我的协议？（`take`，要具体到规则/表/阈值）
   - 它和其它成员冲突在哪？（进 `decide`）
4. **合成协议**：按"实际动手顺序"排步骤，每步吸收最合适的那个技能的做法，并注明 `from`。
5. **写两个文件**：JSON 先写（结构化，便于校验），MD 后写（把 JSON 展开成有判断力的正文）。
6. **自检**：跑 `node scripts/verify-capabilities.mjs <domain>`（由主控提供），必须 0 错误。

---

## 六、禁止事项

- 禁止编造技能名（校验会对账 `catalog.json`）。
- 禁止把原文整段复制进 MD（>60 字连续雷同即视为复制；要改写为判断力）。
- 禁止只写"步骤名"不写"怎么做"（`detail` 少于 40 字的能力卡直接退回）。
- 禁止在能力卡里写"调用 X 技能"作为执行动作（技能不是可执行体，招法才是）。
- 禁止跨域写文件、禁止改 `lib/`、`index.js`、`package.json`。
- 禁止把某台机器的事实（本机装了 R 4.6.1、EndNote 21.5）写成对所有用户的要求；要区分"若本机有"与"若没有则"。
