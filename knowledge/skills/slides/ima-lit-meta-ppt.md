# IMA 知识库文献 → 综述 + Meta 分析 + PPT 全流程

## 适用场景

用户提出：基于（我的）IMA 知识库某个专题，写综述 / 做系统评价 / 做 Meta 分析 / 做科研汇报 PPT。

## 环境准备（Windows / Git Bash 注意）

1. **Bash 环境可能损坏**：若报 `dirname: command not found` 且基础命令不可用，先修复 PATH：
   ```bash
   export PATH="/c/Users/<u>/.workbuddy/binaries/PortableGit/versions/1.2.0/bin:/c/Users/<u>/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:/c/Users/<u>/.workbuddy/binaries/node/versions/22.22.2-3:$PATH"
   ```
2. **绝不用 execSync 拼 shell 调用 ima_api.cjs**（Windows 引号/特殊字符会破坏 JSON）。改为在 Node 脚本中直接 `require`：
   ```js
   const { imaApi } = require('C:/Users/<u>/.workbuddy/skills/ima-skill/ima_api.cjs');
   const resp = JSON.parse(await imaApi('openapi/wiki/v1/get_knowledge_list', {...}));
   ```
   凭证自动从 `~/.config/ima/{client_id,api_key}` 读取，无需传 OPTS。
3. **kb_id 双通道**：MCP 接口用数字 ID；openapi（ima_api.cjs）用 base64 ID。两者不能混用，混用报 `invalid knowledge_base_id`。

## 流程

### 第 1 步：拉取知识库全清单
```js
// 分页拉取，保存 kb_full_list.json

while (!end) {
  const r = JSON.parse(await imaApi('openapi/wiki/v1/get_knowledge_list',
    { knowledge_base_id: KB_B64, cursor, limit: 50 }));
```

### 第 4 步：结构化数据提取（Meta 分析用）
- 按行/句子扫描，筛出"含 ≥2 个血管名（或多因素名）+ 数字"的上下文窗口
- 归一化空白后按句号切分，取前后各 1 句拼接
- 逐篇人工核读，构建 `{研究, 年份, 国家, 分母定义, 分母n, 各条目k}` 数据集

### 第 5 步：自实现 Meta 分析（无 scipy 依赖）
单臂比例 Meta 分析：
```python
def ft(k, n):   # Freeman-Tukey 双反正弦
    t = asin(sqrt(k/(n+1))) + asin(sqrt((k+1)/(n+1)))
    return t, 1.0/(n+0.5)
# DL 随机效应：tau2 = (Q-dfree)/C, C = sum(w) - sum(w^2)/sum(w)
# 逆变换：p = sin(t/2)^2
```
卡方上尾函数（避免 scipy）：级数展开（x<a+1）+ 连分式（x≥a+1）实现正则化不完全伽马函数。

## 比例 Meta 分析的 14 类致命陷阱（实战教训，务必逐条检查）

单臂比例 Meta（各分支/各部位的**构成比**）是临床研究高频需求，但极易出错。以下每条都来自真实翻车：

### 陷阱 1：把各分支的合并值相加当作"区域合计"

**错误**：把"臀上 25.4% + 骶外侧 16.2% + 髂腰 15.5%"相加得"后干 57.1%"，并声称"后干 > 前干"。
**为什么不成立**：FT / logit 等变换 + 随机效应是**非线性**的，独立合并值的线性组合**不等于**区域整体的合并比例，且该"合计"**没有置信区间**，无法做任何统计推断。
**正确做法**：把区域当作**复合结局**——对每项研究先求和该区域各分支的 k（Σk），再除以该研究分母，然后对研究做 FT+DL 合并。同时并列报告"粗构成比（Σk/ΣN，无 CI）"作为描述性对照。
**实例教训**：错误相加得 57.1% vs 41.3%；正确复合合并得 51.0% (29.0–72.8) vs 40.3% (21.9–60.2)，**CI 大幅重叠 → 差异不显著**；而粗构成比是 60.3% vs 32.7%。三种算法差异巨大，结论表述完全不同。

### 陷阱 2："缺失 = 0" 还是 "成对删除"？必须用闭合检验判定

某研究未列出某分支，到底是"该研究未见此损伤（=0）"还是"未报告（应剔除）"？这决定合并结果是否可比。

**判定方法（闭合检验）**：把每项研究所列各分支的计数**求和**，与其报告的分析分母比较：
- 若 **Σk = 分母**（如 129 = 129、49 = 49、21 = 21）→ 原文已完整列出分布，**"缺失 = 0"成立**，可用统一分母，构成比在计数层面闭合至 100%
- 若 Σk ≠ 分母 → 存在未报告项，**只能用成对删除（pairwise deletion）**，并必须在表注声明"各分支纳入研究数不同、构成比之和不等于 100%"

**为何重要**：成对删除下各分支的研究集合与分母都不同（本实例 3/2/1 项、199/150/129），10 个分支的合并值之和可达 **105.6%**，审稿人会直接质疑"构成比为何超过 100%"。

### 陷阱 3：稀疏列联表的置换检验必须固定边际

**错误**：把列联表的全部单元格值打乱后重排（完全随机化）再算 χ²——此时**行合计与列合计都被破坏**，置换分布完全失真。
**实例教训**：4 分型 × 10 血管的稀疏表（80% 格子期望频数 <5），错误做法得到 **p = 1.0000**（观测 χ² 低于所有置换值，因为随机表的行合计差异极大）；正确做法得到 **p = 0.5564**，与经典渐近值 0.5407 吻合。
**正确做法**：**序贯条件抽样**（Patefield 型）——逐行从多元超几何分布中抽样，末行由约束决定，从而精确保持边际：
```python
def sample_fixed_margin(rowsums, colsums, rng):
    cols = colsums[:]; rows = []
    for i in range(len(rowsums) - 1):
        n, total, row = rowsums[i], sum(cols), [0]*len(cols)
        for _ in range(n):
            r, cum = rng.random() * total, 0
            for j, c in enumerate(cols):
                cum += c
                if r <= cum and c > 0:
                    row[j] += 1; cols[j] -= 1; total -= 1; break
        rows.append(row)
    rows.append(cols[:])
    return rows
```

### 陷阱 4：k < 10 时 Wald 置信区间偏窄，必须补 HKSJ

小研究数下 Wald CI 会系统性过窄。必须补 **HKSJ（Hartung-Knapp-Sidik-Jonkman）** 校正：
```python
# 在合并尺度（如 FT 变换后的 t 尺度）上：
w_i = 1 / (v_i + tau2)
t_re = sum(w_i*t_i) / sum(w_i)
q = sum(w_i * (t_i - t_re)**2) / (k - 1)      # 关键校正项
se_hksj = sqrt(q / sum(w_i))
ci = t_re ± t.ppf(0.975, df=k-1) * se_hksj    # 用 t 分布而非正态
```
**实例教训**：除 I²=0 的分支外，HKSJ CI 普遍约为 Wald 的 **2 倍宽**（臀上 16.1–36.1 → 8.6–47.3）。主表可保留 Wald，但敏感性分析必须并列 HKSJ，并在 Limitations 说明。

### 陷阱 5：二次数据必须排除

系统综述/叙述性综述报告的"合并百分比"是**二次数据**，纳入会与原始研究重复计数、虚增权重。识别特征：标注 "pooled"、"systematic review"、分母为整数 100 等。
**处置**：排除出主分析，仅可作背景引用。

### 陷阱 6：左右侧分开报告的研究不可简单相加

按 left / right 分别报告"患者数"的研究，左右相加会**把双侧损伤的患者重复计数**。
**判据**：比较 Σk 与报告的总患者数。若 Σk > n（如 128 > 104），说明存在双侧或多支损伤。
**处置**：① 若该研究给出了左右**合并值**（如"右和/或左 = 27 例"），仅采纳该血管的合并值；② 未给合并值的血管**不纳入合并**；③ 不得进入患者级分析（无法从分侧计数还原患者数）。

### 附：口径分层是异质性的首要来源

当同一结局存在多种分母口径（**病灶数 / 血管支数 / 患者数 / 患者数(按侧) / 合并百分比**）时：
- 先做**口径分层亚组分析**（Q_between 检验），若各口径间 Q_between p < 0.001 → 口径是异质性主导来源
- **主分析必须限定单一口径**，其余口径作敏感性分析；**不同口径绝不可混池**（实例：混池时 I² 高达 81–97%，分层后部分分支降至 0–26%）
- 标题、摘要、图注必须明确标注当前结果属于哪种口径；**病灶构成比（topography）≠ 患者级风险（patient-level risk）**，禁用"发生率/发病率"描述构成比

### 陷阱 7：Freeman-Tukey 反变换必须截断值域 t ∈ [0, π]（已两次造成实际错误）

**症状 A（CI 倒置）**：出现 "17.9 (83.2–7.4)" 这类上界小于下界的区间。
**症状 B（虚假正下界）**：极低占比分支（如占比 2.9%）的 HKSJ 下界反而**高于** Wald 下界（如 HKSJ 1.5% > Wald 0.3%）——**下界升高是非单调的直接信号**。

**根因**：FT 变换 `t = asin√(k/(n+1)) + asin√((k+1)/(n+1))` 的**值域是 [0, π]**；而 `p = sin²(t/2)` **仅在 [0, π] 上单调**。当合并中心 ± 1.96·SE 落到 [0, π] 之外时：
- `t < 0`：`sin²(t/2)` 开始**反向增大** → 虚假正下界
- `t > π`：同样反向减小 → 虚假低下界

**正确写法（必须）**：
```python
def inv_ft(t):
    t = max(0.0, min(math.pi, t))      # ← 关键：先截断到 FT 值域
    return max(0.0, min(1.0, math.sin(t/2) ** 2))
```
**为什么必须显式截断而非依赖 `max(0, ...)`**：`max(0, sin²(t/2))` 对负 t 无效——`sin²` 恒 ≥ 0，越界的负 θ 会被"反射"成一个**看似合理的正值**，静默出错。**这类错误不会报错、不会崩溃，只会给出错误的数字。**

**自检方法（每次算完必须跑）**：
```
❶ 下界是否 ≤ 合并值 ≤ 上界？（单调性）
❷ 极低占比分支的 HKSJ 下界是否 ≥ 对应 Wald 下界？（合理性——HKSJ 更保守，下界不应升高）
❸ 是否存在 θ 尺度下界 < 0 的情形？（若有一律输出 0.0）
❹ CI 宽度比是否始终 ≥ 1？（HKSJ/Wald 之比 < 1 只在 I²=0 时合理）
```

**实例**：3 项研究的比例 Meta 中，膀胱动脉（2.9%）、骶正中动脉（2.2%）、腰动脉（0.8%）三个低占比分支的 HKSJ/Wald 下界全部出错（应为 0.0），而上界与其余 9 个分支完全正常——**只有下界受影响**，极易漏检。

### 陷阱 8：稀疏数据下"合并"可能根本不可行——先算 k，再决定是否合并

剔除口径错误与高风险研究后，某域的可用研究数可能**塌缩到 k≤2**。此时：
- **不要硬做合并**（k=1 无合并可言；k=2 的随机效应 τ² 与 CI 均不可靠）
- **改为描述性报告**：直接列出各研究的单个数值（k/n 与 %）
- 并把"该域证据不足以合并"本身作为**结论**写入正文与局限——这通常比强行给出一个不稳健的合并值更有价值

**判据**：某分支/某域 **k=1** → 报单一研究值（标注"未作合并"）；**k=2** → 报两个研究的单个值 + 说明不合并理由；**k≥3** 才考虑合并，且须报告 I² 与 τ²。

### 陷阱 9：成对删除 vs 缺失=0 —— 必须核对引擎的实际行为

**同一个 `pool()` 函数，对"某研究未列出某分支"的处理方式不同，结果完全不同**：
- **成对删除**（pairwise deletion）：未列出 → 该研究不进入该分支的合并（各分支研究集合不同，占比之和 ≠ 100%）
- **缺失=0**：未列出 → 视为该研究未见该分支损伤（k=0 显式补行），统一分母，占比可闭合

**危险点**：多数长表结构引擎（直接读原始长表）**默认等价于成对删除**——因为未列出的分支根本没有行。要用"缺失=0"，必须**显式补齐 k=0 行**。

**必做核对**：对每个分支打印"纳入研究数"，若同一分析中不同分支的纳入研究数不一致（如 3/2/1），说明是成对删除；此时必须在表注声明"各分支归属不同、占比之和不等于 100%"，或改用缺失=0。

### 陷阱 10：手工修正产物后未回写生成脚本 —— 可复现性被静默破坏

**现象**：多轮迭代中，研究者发现并手工修正了产物 CSV 中的错误（如血管名错位、study_id 标签错位、分母口径），但**忘记同步修改生成脚本**。此后任何人重跑该脚本，就会**把这些修正全部回退**，且不会报错——产物"看起来正常"，只是悄悄变回错误值。

**真实案例**（本项目）：
| 脚本位置 | 脚本值（未同步） | 产物值（已修正） | 重跑后果 |
|---|---|---|---|
| `build_datasets.py` L151 | `{'LSA':4,'SGA':3,'IPA':5}` | `{'ILA':4,'LSA':3,'Obturator':5}` | 血管名错位回退（结论指向错误血管） |
| 同 L192 | `study_id='S14'` | `'S3'` | 研究标签错配回退 |
| 同 L102-104 | `scope=patients, nden=45` | `responsible-vessel count, 52` | 分母口径修正回退 |

**防御措施（必须执行）**：
1. **每次手工修正产物后，立即在生成脚本中定位对应代码并同步**
2. **同步后必须重跑脚本 + diff 验证**：`diff <(重跑前产物) <(重跑后产物)` 应仅显示预期的标签差异，**实质数值零变化**
3. **若脚本已被废止**，明确加 `DEPRECATED` 抬头（不删除，保留证据链），并在 `INDEX.md` 登记
4. **建立"产物 ↔ 脚本"对照表**：列出每个数据文件由其哪个脚本生成，便于日后核查

**检查清单**（交付前）：
- [ ] 每个"手工修正过"的产物，其生成脚本是否已同步？
- [ ] 重跑所有生成脚本，产物是否与当前交付版本一致（diff=0）？
- [ ] 是否存在"已失效但未标记"的旧脚本？

### 陷阱 11：CSV 转义缺陷 —— Excel 看不出、pandas 才报错

**现象**：字段内含逗号（如 `"author A, author B"`）或中文括注未加引号转义，导致列错位。**Excel 打开时可能显示正常**（因为它按显示宽度对齐），但 `pandas.read_csv()` 会报 `Expected N fields, saw N+1`。

**真实案例**：`quality_assessment.csv` 的 S10 行因 note 字段含未转义逗号，导致该行多出一列、后续行错位。

**防御措施**：
1. **生成 CSV 时一律使用 `csv.writer`**（自动处理转义），不要手写字符串拼接
2. **交付前用 pandas 全量读取校验**：`pd.read_csv(f)` 不报错且 `shape` 符合预期
3. **写入含逗号/引号/换行的字段时**，确保使用 `quoting=csv.QUOTE_MINIMAL`（默认）且字段值本身不破坏结构
4. 中文括注如 `(张英泽)` 本身安全，但 `(author A, author B)` 类含逗号的内容必须转义

### 陷阱 12：技术标识 vs 显示标签 —— 改名时容易误伤

**场景**：发现某处数据字段错误（如年份、刊名），需要全局更正。若不加区分地统一替换，会**破坏数据链路**。

**正确做法：区分两类标识**
| 类型 | 定义 | 处置 |
|---|---|---|
| **技术标识（id）** | 数据主键（`study_id` 列值）、脚本 dict 键、JSON 键、BibTeX 键、文件名、图表编号 | **一律不改**——改动会破坏脚本引用与可复现性 |
| **显示标签（label）** | 正文/表格单元格/图注中的人类可读文本、`study_label` 列、`year` 列 | **更新为正确值** |

**并在文档中登记映射关系**：
> "`study_id` 为数据链路技术标识（保持建立时取值）；显示标签采用核实后值：`Fu2011`(id) = Fu 2012（刊年）、`Chen2013`(id) = Chen Y 2002（刊年）。"

**执行注意**：原清单的 grep 模式可能漏检格式变体（如 `Fu\s?2011` 匹配不到中间夹名字的 `Fu CY,2011`）——**改完必须用多种模式复检**，并人工抽查关键表格。

### 陷阱 13：修正只做一半 —— 改了数据/脚本，未改描述文档与下游消费者

**现象**：多轮迭代中修正一处数据后，只更新了"直接相关的文件"，而**下游消费者**（描述文档、汇总表、情景对照表、图表生成器）未同步，造成"数据文件是新值、文档写旧值"的静默不一致。

**真实案例**（本项目同一问题出现 3 次）：
| # | 修正内容 | 未同步的下游 | 后果 |
|---|---|---|---|
| 1 | 手工修正 `dataset_A`/`dataset_B` | `build_datasets.py`（生成器） | 任何人重跑即回退全部修正 |
| 2 | 患者域改为描述性报告（裁定） | `run_pairwise_sensitivity.py` 的 3b 段 | 补充材料仍含废弃合并值 + 已剔除研究 |
| 3 | `data_expanded.csv` 的 Huang2016 口径 45→52 | `RESULTS_MAIN.md` §5.1/§5.2 情景对照表 | 文档记录旧值（如 IPA 33.4%），与数据文件矛盾 |

**根因**：每次都"只改了直接触发问题的那个文件"，未追踪**所有消费者**。

**防御措施 —— 建立"修正影响面清单"**：
每次修正后，**必须逐一核对以下五类消费者**：
```
修正一处数据/口径
  ├─ ① 数据文件本身（CSV/JSON）
  ├─ ② 生成器脚本（改后必须重跑 + diff 验证）
  ├─ ③ 下游派生数据（汇总表/对照表/情景表）
  ├─ ④ 描述性文档（Results/README/方法论说明中的数值引用）
  └─ ⑤ 表图（含生成脚本 + 已导出的 docx/xlsx/png）
```
**核查方法**：用**被废弃的旧值**做全局搜索（如本例搜 `34.7`/`33.4`/`18.6`）——命中即表明有下游未同步。这是最有效的检测手段。

**汇报纪律**：修正后应主动说明"影响面覆盖情况"（已核对①②③④⑤，或"仅完成①②，③④⑤待处理"），而非仅报告"已修正"。

### 陷阱 14：多智能体协作时的并发写冲突 —— 同一文件必须单人串行编辑

**现象**（多智能体/多人协作场景高发）：
- **跨成员并行编辑**：主理人代执行修正时，原归属成员也在编辑同一文件 → 双方各改一部分；若一方是"整文件重写"型脚本，会**直接覆盖**另一方已落盘的编辑
- **同成员消息内多次 Edit**：同一条消息里对同一文件并行多次 Edit → 互相覆盖、只部分落盘

**真实案例**：本项目 `RESULTS_MAIN.md` 被主理人与 causal-analyst 同时编辑，导致该成员的整批编辑一度被整文件重写回退（需重放修复）；另一次"作废说明"被两方各写一遍（重复）。

**探测信号**：**替换串部分不匹配**——当你准备的 `old_string` 在文件中找不到，但又不是完全不存在时，往往意味着文件已被他人改动。

**防御措施（必须执行）**：
1. **同一文件同一时间只允许一个写入者** —— 协作前先明确"谁负责哪个文件"
2. **代执行前先通知原归属成员**："我将代执行 X 文件，请暂停编辑"——并等其确认
3. **优先用追加或精确替换，避免整文件重写** —— 重写型脚本是高危操作，必须在头部加 `⚠️ 请勿重跑` 标注
4. **写入前重读文件**（不要用几分钟前的快照做替换）
5. **写后立即 diff 自查**：确认变更范围符合预期（如"恰为 4 行"），超范围即中止排查
6. **hash 锁定核验**：核验报告记录被核验版本的 sha256；任何后续写入须以新 hash 重验

**配套：核验版本锚定**
```
mtime / bytes / sha256 三项记录在核验报告中
→ 后续任何修改均使核验失效，需增量重验（重跑核验脚本 + 更新锚点）
```

## 验证链条（投稿级必备，至少两条独立路径）

1. **自编双实现**：主实现 vs 精确闭式（如 Erlang/erfc 闭式 χ²、erf 二分求逆）
2. **第三方库复算**：`scipy.stats.chi2.sf` / `t.ppf` / `norm.ppf`
3. **他人独立复跑**：换一个 agent 用同一引擎跑同一数据
4. **跨环境纯标准库重写**：不依赖 numpy/scipy，暴露环境依赖型缺陷
5. **交叉复核他人的计算**：让另一位成员独立重算**主理人/他人**的中间结果——本次正是靠这一步发现了 HKSJ 下界 3 处错误

每条路径的差异必须落在数值精度内（<0.1 个百分点）。**留证**：把对比表写进 `METHOD_NOTES.md` 的验证章节，并在正文 Methods 中说明验证方式（这反而增强可信度）。

**注意**：交叉复核不是"确认无误"的形式主义——每一条独立路径都可能发现真实缺陷。本次四条路径分别发现了：① 自编双路径 → chi2 函数 df 误用与奇 df 递推符号错；② 第三方库 → 无；③ 他人复跑 → 引擎默认成对删除的口径歧义；④ 交叉复核 → HKSJ 反变换缺截断（3 处下界）。

## 交付格式铁律：文字成果必须是 Word（.docx）

> **用户明确要求（2026-09-17）**：文字性质的东西（论文稿、报告、说明、清单、索引、参考文献表、图注）**一律交 Word**，不要给 Markdown——"我下下来也没法用啊"。Markdown 只能作中间产物。

**格式分配规则**

| 交付物性质 | 格式 |
|---|---|
| 论文稿 / 报告 / 说明 / 清单 / 索引 / 参考文献表 / 图注 | **.docx**（严禁 .md） |
| 表格（三线表） | .docx；多表汇总用 .xlsx |
| 文献合集 | .xlsx（含标题与 DOI） |
| 统计结果 / 原始数据 | .csv / .json |
| 图形 | .png（300dpi）+ .pdf（矢量） |

**保真转换做法（`md2docx.py` 模式，只映射格式、不改一字）**

1. **块级解析**：标题（1–4 级）/ 表格 / 有序·无序列表 / 引用 / 分隔线 / 代码块 / 段落
2. **行内解析**：`**粗体**` / `*斜体*` / `` `代码` `` / `<sup>` / `<sub>` / `[链接](url)`
   - ⚠️ **代码跨度必须先切分**：`file.*` 这类带星号的文件名若与另一处 `*` 同行，会被斜体正则跨段匹配并**吞掉内容**。正确做法是先用 `` (`[^`\n]+`) `` 切分整行，代码段内不做强调解析
   - ⚠️ 斜体用严格规则：`(?<!\*)\*(?=[^\s*])[^*\n]+?(?<=[^\s*])\*(?!\*)`（开符后非空白、闭符前非空白），避免把表格脚注的 `*` 误当斜体
   - ⚠️ 还原 `\*` 转义（否则反斜杠残留进正文）
3. **版式**（中华医学会稿约）：A4 + 上下 2.54 / 左右 3.17 cm；正文宋体小四（12pt）+ 行距**固定值 20 磅** + 首行缩进 2 字符（用 `w:firstLineChars="200"`）；标题黑体分级（H1 三号居中 / H2 四号 / H3 小四 / H4 五号）；**三线表**（顶线 1.5pt、表头线 0.75pt、底线 1.5pt，其余 `w:tblBorders` 全 none）；`<sup>[n]</sup>` → `run.font.superscript = True`；页脚居中页码
4. **中文字体必须设 `w:eastAsia`**：`run.font.name` 只管西文，中文须单独 `rPr/rFonts.set(qn('w:eastAsia'), '宋体')`
5. **交叉引用同步**：转换后文稿内的文件名引用（如"见 `xx.md`"）须一并改为 `.docx`，否则包内引用断链
6. **打包路径同步**：文稿里的图表清单路径应改为交付包相对路径（`02_表格/...`、`03_图形/...`）

**必做核验（`verify_docx.py` 模式）**

| 核验项 | 判据 |
|---|---|
| **逐行覆盖率** | 源 md 每一"实质行"（≥8 字符）都能在 docx 中找到 → 目标 100% |
| **数字命中率** | 源 md 中所有数字串在 docx 中齐全（如手稿 245/245） |
| **上标数** | docx 上标 run 数 == 源 `<sup>` 标签数（正文引注），且参考文献列表的 `[n]` **不得**为上标 |
| 表格数 | docx 表格数 == 源 md 表格数 |
| 版式参数 | 页面尺寸 / 边距 / `eastAsia` / `lineRule="exact"` / `firstLine` / `tcBorders` 计数均 > 0 |
| 文件完整性 | 每个 docx 通过 `zipfile.testzip()`；ZIP 内 UTF-8 标志数 == 条目数 |

**核验脚本自身也会假阴性**——报错时先判定是**产物问题**还是**核验方法问题**，再决定是否改产物。本轮三次误报的成因：① 表格单元格被拆成独立行比对（应按行拼接）；② 表格行首尾 `|` 字符未剥离；③ `\*` 转义符未剥离 / 探针手误。**盲目"修产物"会破坏正确内容**。

## 交付打包规范（ZIP）

| 要点 | 做法 |
|---|---|
| 不改源文件名 | 正文/图表清单按原文件名引用；打包用 `arcname` 映射目录结构，不复制、不移动源文件 |
| 缺文件即报错 | 打包前预检 `os.path.isfile`，**任何一项缺失就中止**，不允许静默跳过 |
| 中文文件名兼容 | Python `zipfile` 自动为非 ASCII 名设 UTF-8 标志（bit 11）；打包后**验证 `flag_bits & 0x800` 数量 == 条目数**，否则 Windows 资源管理器解压乱码 |
| 打包后校验 | `testzip()` CRC 测试 + 条目数核对 + 抽查关键文件可解压 + 打印完整清单 |
| 附录说明 | ZIP 内放 `00_交付说明.md`：目录结构、**图表↔文件对应表**（含"文件名是内部标识、图号以本表为准"说明）、核心结果速览、投稿前待办 |
| 顺序 | **先修正已知问题（含参考文献）再打包**——否则打包的是带错版本，还得重打 |

**典型包结构**：`00_交付说明.md` / `01_论文与报告/` / `02_表格/` / `03_图形/` / `04_检索记录与关键数据/`。
