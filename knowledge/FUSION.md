# 719 个 SKILL 的整理与融合规则（v2）

这份文件回答一个问题：**包里明明有 719 个技能，为什么模型不该在这 719 个里挑一个，而要走能力卡？**

## 一、为什么不是路由器

v1 用的是「任务原型 A1–A17 → 每阶段一个首选技能 + 若干备选」的链路。它在演示里看着很顺，实际用起来有两个硬伤：

1. **首选位上放谁，取决于写路由表的人的偏好，而不是技能本身的强弱。** 同一个能力常有 3～5 个技能都做，各自的深度不一样：有的给完整判据和阈值，有的只给一句口诀；有的能离线跑，有的必须联网或付费。用"首选"这个位置表达这种差异，等于把多维权衡压成一个名次，压掉的信息恰好是决定成败的那部分。
2. **它会诱导模型宣布"我将使用 XX 技能"。** 用户拿到的是一句技能名，不是方法：为什么这么切、阈值是多少、哪一步不许跳，全在技能正文里，用户既不掌握也无法校验。而多数技能正文的真实形态是一份**自我说明**（我擅长什么、什么时候用我），不是一份**可执行方法**。

v2 把融合单元从"技能"换成**能力卡（capability card）**：一张卡对应一件用户真正要办的事（如`stats.psm`、`figures.mechanism`、`literature.fact-check`），卡里同时装着这个能力的**方法与判据**、以及**参与这件事的几个技能各自站什么位置**。模型按卡走，用户看到的是一套方法；技能退到"证据参考"的位置，需要时用 `research_kb_read` 读原文。

## 二、整理规则

1. **全量打包，不做筛选**：719 个 `SKILL.md` 逐字收进 `knowledge/skills/<域>/<slug>.md`，一个不丢。理由：融合一定会有判断失误，把落选的技能也留在包里，模型可以自己翻原文纠正我。
2. **同名保留**（`scientific-visualization`、`memory-setup`、`docx` 各 2 份），以目录名限定 slug 区分，不覆盖。
3. **域标签只作参考，不作依据**：`knowledge/catalog.json` 的 `domain` 是按名称/描述关键词打出来的，噪声很大——`stats` 域 180 条里混着模型训练、金融交易、单细胞工具；`polish` 域 24 条里 10 条与润色无关。所以能力卡是**人工逐域梳理**出来的，不是按标签自动汇总。
4. **科研相关性标记** `research: true`（489 个）只用于检索加权与索引展示，不参与能力卡构建。
5. **通用域（`general`，88 条）不进融合**：它们多是与科研无关的工程/生活技能，仅编目留档。

## 三、融合单元：能力卡

`data/capabilities/<域>.json` 共 **9 域 81 张卡**，每张卡是一个对象，字段含义：

| 字段 | 含义 |
|---|---|
| `id` | 能力标识，形如 `<域>.<能力>`，全局唯一 |
| `label` / `summary` | 用户语言里的名字与一句话定义（用户要做的事，不是技能名） |
| `triggers` | 触发词。`research_playbook` 用它在用户原话里做匹配 |
| `members[]` | 参与技能清单，每项含 `skill`、`role`、`best_at`、`limits`、`take` |
| `protocol[]` | 融合后的执行协议，每步含 `step`、`from`（取自哪个技能）、`detail`（怎么做，带阈值） |
| `divergence[]` | 同功能技能之间的分歧点：什么条件下按 A，什么条件下按 B |
| `gates[]` | 判据与红线：交付前必须逐条核的机械可检项 |
| `deliverables[]` | 交付物形态 |
| `kb[]` | 需要读原文时优先读哪几个技能 |
| `skill` | 该域对应的融合技能文件名（`research-<域>`） |

`members[].role` 四档，是本插件对"取长补短"的具体落地：

- **主用（primary）**：承担该能力的骨架流程，判据最完整、覆盖最常见的路径。
- **补强（support）**：在它最擅长的单点替换主用——不是"更弱的备选"，而是"这一小步它更好"。
- **兜底（fallback）**：主用与补强都跑不通时（缺依赖、缺脚本、环境不满足）的退路，通常在 `limits` 里写清代价。
- **弃用（deprecated）**：同名能力里有明显缺陷、或与发布版边界冲突的技能，**登记在册并写明为什么不用**，防止后来的人重新踩进去。`figures` 域弃用 5 条（数据出机、只出位图、不可复现），`polish` 域弃用 `sepia`（虚构文体）、`paper-checker`（依赖外部检测服务）。

每张卡都至少含一个补强或兜底或弃用成员——这是 `scripts/verify-capabilities.mjs` 强制检查的，防止有人把一张卡写成"首选技能"的复述。

## 四、执行纪律

1. **先选能力，不选技能**：入口技能 `research-suite` 规定第一步永远 `research_playbook(task=<用户原话>)`，并明令禁止在回答里说"我将使用 / 首选某个技能"。
2. **不跳步**：`protocol` 是顺序协议，不是清单；跳过任一步都要在交付说明里写明跳了哪一步、为什么、风险是什么。
3. **分歧点按条件走**：`divergence` 里每一对分歧都写成"若 <条件> 则按 A，否则按 B"，模型按当次任务的数据与场景选，不按名气选。
4. **判据先于结论**：`gates` 在交付前逐条核；机械可检的项用 `research_gate(text=...)` 跑一遍（全角标点、AI 套话、绝对化措辞、文言腔、引用编号格式）。
5. **深读最多 2 个**：只有 `kb` 里点名的技能值得读全文，其余凭卡片信息执行；读全文是为了核对"这条判据到底怎么写的"，不是为了重抄一遍 SOP。

## 五、规模与覆盖

| 项 | 数值 |
|---|---:|
| 原技能总数 | 719 |
| 科研相关 | 489 |
| 能力域 | 9（+1 通用域不进融合） |
| 能力卡 | 81 |
| 被能力卡引用的技能 | 177 |
| 仅编目留档 | 542 |

域分布：`writing` 11、`polish` 5、`figures` 9、`stats` 16、`ideation` 7、`review` 8、`slides` 7、`literature` 11、`format` 7。

被引用 177 / 719 是**刻意**的：能力卡是给"写论文的人"用的执行方法，不是技能大全。剩下 542 个技能留在包里，作用是当主用技能描述不够、或遇到偏门场景时，模型可以 `research_catalog` 检索后 `research_kb_read` 读原文自助。索引见 `knowledge/INDEX.md`。

## 六、融合时发现的真问题（写在这里防止复现）

1. **技能正文的真实形态是自我说明，不是方法。** 大量技能只写"我擅长 X，适合 Y 场景"，把阈值、判据、常见错误留给想象。融合时凡遇到这种，必须补出可检判据（例如润色的"字数变动 ±5%""句长比 4:1""段内 4～8 句"），否则卡里就会留下"注意质量"这类废话。
2. **同名能力之间常常不是强弱关系，而是场景错配。** 例如 `paper-deweight` 与 `paper-polisher` 是互斥场景（学术语体去 AI 痕迹 vs Word 精修留痕报告），写进 `mutex` 而不是排成一二名。
3. **有些技能的核心能力外包给了第三方服务。** 在线绘图 API、外部生图、AI 检测服务、付费修复工具——发布版必须能离线独立跑，这类技能只能降级或弃用，并在卡里写明替代路径。
4. **全库没有的东西要如实说没有。** 没有专职 meta-analysis 技能（`metafor` 零命中）、没有任何技能提供影响因子/审稿周期/录用率。这两处都写成了机械门：Meta 由 `ima-lit-meta-ppt` 支撑并在来源索引标注真实路径；期刊数字"出现次数＝0"。
