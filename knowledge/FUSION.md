# 592 条源记录的判定与融合规则（v3）

这份文件回答一个问题：**包里明明有 592 条技能记录，为什么模型不该在里面挑一个，而要走能力卡？**

v3 相比 v2 的三处变化：源全集换成用户 2026-11-06 打包的精选全集（719 → **592 条记录 / 586 个技能目录**，剔掉 162 条错标的非科研技能，新增 35 个此前未收录的插件内置技能）；新增 **`data` 域**（数据库取数与组学解析）；**每个源技能都有一行判定账本**，不再有"落选了但没人知道为什么"的技能。

## 一、为什么不是路由器

v1 用的是「任务原型 A1–A17 → 每阶段一个首选技能 + 若干备选」的链路。它在演示里看着很顺，实际用起来有两个硬伤：

1. **首选位上放谁，取决于写路由表的人的偏好，而不是技能本身的强弱。** 同一个能力常有 3～5 个技能都做，各自的深度不一样：有的给完整判据和阈值，有的只给一句口诀；有的能离线跑，有的必须联网或付费。用"首选"这个位置表达这种差异，等于把多维权衡压成一个名次，压掉的信息恰好是决定成败的那部分。
2. **它会诱导模型宣布"我将使用 XX 技能"。** 用户拿到的是一句技能名，不是方法：为什么这么切、阈值是多少、哪一步不许跳，全在技能正文里，用户既不掌握也无法校验。而多数技能正文的真实形态是一份**自我说明**（我擅长什么、什么时候用我），不是一份**可执行方法**。

v2 起的做法是把融合单元从"技能"换成**能力卡（capability card）**：一张卡对应一件用户真正要办的事（如 `stats.psm`、`figures.mechanism`、`literature.fact-check`），卡里同时装着这个能力的**方法与判据**、以及**参与这件事的几个技能各自站什么位置**。模型按卡走，用户看到的是一套方法；技能退到"证据参考"的位置，需要时用 `research_kb_read` 读原文。v3 沿用这个模型，只是把"谁被怎么用了"从卡里的一句话，扩成**每域一份账本**。

## 二、整理规则（v3）

1. **全量收、逐条判、不静默丢**：592 条记录全部进 `knowledge/skills/<域>/<slug>.md`，并在 `data/ledger/<域>.json` 里为每一条写一行判定——`fused`（融进某张卡）、`index-only`（留档检索）、`deprecated`（在册但不用，写明为什么）、`out-of-scope`（不属于本域，写明该归哪）。`scripts/verify-ledger.mjs` 用目录集合对账，**漏一条或多一条都算错**。
2. **同名保留**：6 组同目录重复记录（`scientific-visualization`、`pdf`、`pdfkit-py`、`research-grants`、`literature-review`、`scientific-writing`）各计一条账本，因此账本总数为 **586**；`knowledge/catalog.json` 保留 592 条原记录以便追溯来源。
3. **域标签只作参考，不作依据**：全集自带的分类是关键词打出来的，噪声不小（`stats` 域里有模型训练与金融数据工具，`polish` 域里有 10 条与润色无关）。v3 的域归属是**人工逐条过**的（`analysis/assign-domains.mjs` 的 MANUAL 表钉死内置技能与错标技能），共 10 个能力域 + 1 个工具箱索引桶。
4. **工具箱不进融合**：`toolbox` 233 条是科学计算库、ML 工程、airs 工具族、通用办公等，与科研写作无直接关系。它们只在账本里留 `index-only`，`research_catalog` 可检索借用，但**不建卡**——建卡会让能力面虚胖。
5. **随包资产按预算收**：技能自带的 `references/`、`scripts/`、`templates/` 用白名单扩展名收进 `<slug>__assets/`，单文件 ≤256KB、单个用户级技能整包 ≤260KB、内置技能 ≤5MB。超预算的**整包不收**（不搞残缺脚本集），账本与 `catalog.assets` 里写明 `included:false` 和"本来有多大"。实测 451 个技能带资产、3924 个文件、约 29MB。

## 三、融合单元：能力卡

`data/capabilities/<域>.json` 共 **10 域 103 张卡**，每张卡是一个对象：

| 字段 | 含义 |
|---|---|
| `id` | 能力标识，形如 `<域>.<能力>`，全局唯一 |
| `label` / `summary` | 用户语言里的名字与一句话定义（用户要做的事，不是技能名） |
| `triggers` | 触发词。`research_playbook` 用它在用户原话里做匹配 |
| `inputs` | 这件事开始前必须具备的输入 |
| `members[]` | 参与技能清单，每项含 `skill`、`verdict`（主用／补强／兜底／弃用）、`best_at`、`limits`、`take` |
| `protocol[]` | 融合后的执行协议，每步含 `step`、`from`（取自哪个技能）、`do`、`detail`（怎么做，带阈值） |
| `decide[]` | 分歧点：什么条件下按 A、什么条件下按 B、为什么 |
| `gates[]` | 判据与红线：交付前必须逐条核的机械可检项 |
| `outputs[]` | 交付物形态 |
| `kb[]` | 需要读原文时优先读哪几个技能（**技能名，不是路径**） |

`members[].verdict` 四档，是本插件对"取长补短"的具体落地：

- **主用**：承担该能力的骨架流程，判据最完整、覆盖最常见的路径。
- **补强**：在它最擅长的单点替换主用——不是"更弱的备选"，而是"这一小步它更好"。例如英文润色卡里 `nature-polishing` 提供四轴路由、`paper-polish` 提供"忠实原意压过一切规则"的越界标注。
- **兜底**：主用与补强都跑不通时（缺依赖、缺脚本、环境不满足）的退路，通常在 `limits` 里写清代价。
- **弃用**：同名能力里有明显缺陷、或与发布版边界冲突的技能，**登记在册并写明为什么不用**，防止后来的人重新踩进去。v3 共 40 余条，典型四类：数据要出机（`xiantao-plot-api`、`xmed-figure`、`scientific-schematics`、`generate-image`）、要付费或账号（`thesis-format-zh`、`cosmic`、`drugbank`）、依赖外部评审/检测后端（`paper-checker`、`aris-auto-review-loop`）、能力外包给第三方服务。

每张卡都至少含一个补强或兜底或弃用成员——`scripts/verify-capabilities.mjs` 强制检查，防止有人把一张卡写成"首选技能"的复述。

## 四、执行纪律

1. **先选能力，不选技能**：入口技能 `research-suite` 规定第一步永远 `research_playbook(task=<用户原话>)`，并明令禁止在回答里说"我将使用 / 首选某个技能"。
2. **不跳步**：`protocol` 是顺序协议，不是清单；跳过任一步都要在交付说明里写明跳了哪一步、为什么、风险是什么。
3. **分歧点按条件走**：`decide` 里每一对分歧都写成"若 <条件> 则按 A，否则按 B"，模型按当次任务的数据与场景选，不按名气选。
4. **判据先于结论**：`gates` 在交付前逐条核；机械可检的项用 `research_gate(text=...)` 跑一遍（全角标点、AI 套话、绝对化措辞、文言腔、引用编号格式）。
5. **深读最多 2 个**：只有 `kb` 里点名的技能值得读全文，其余凭卡片信息执行；技能自带脚本与模板用 `research_kb_read(name=..., asset=...)` 直读，不必整篇读技能。
6. **交付说明里交代用了什么**：哪张卡、过了哪些 gates、留下了什么可复现材料（脚本、数据、manifest）。

## 五、规模与覆盖

| 项 | 数值 |
|---|---:|
| 源记录（catalog） | 592 |
| 唯一技能目录（= 账本条数） | 586 |
| 能力域 | 10（+1 工具箱索引桶不进融合） |
| 能力卡 | 103 |
| 被能力卡引用的技能 | 237 |
| 账本判定 | fused 218 / index-only 76 / deprecated 33 / out-of-scope 41（另 toolbox 233 全 index-only） |
| 随包资产 | 451 个技能、3924 个文件、约 29MB |

域分布（源记录 / 能力卡）：`writing` 66/14、`polish` 12/5、`figures` 36/10、`stats` 31/18、`ideation` 39/7、`review` 21/8、`slides` 37/8、`literature` 26/12、`format` 51/11、`data` 40/10，另 `toolbox` 233/0。

被引用 237 / 592 是**刻意**的：能力卡是给"做科研的人"用的执行方法，不是技能大全。剩下的技能留在包里，作用是当主用技能描述不够、或遇到偏门场景时，模型可以 `research_catalog` 检索后 `research_kb_read` 读原文自助。索引见 `knowledge/INDEX.md`，逐条判定见 `data/ledger/`。

## 六、融合时发现的真问题（写在这里防止复现）

1. **技能正文的真实形态是自我说明，不是方法。** 大量技能只写"我擅长 X，适合 Y 场景"，把阈值、判据、常见错误留给想象。融合时凡遇这种必须补出可检判据（润色的"字数变动 ±5%""句长比 4:1"、统计的"EPV≥10""|SMD|<0.1"、幻灯的"备注 200～210 字/分钟"），否则卡里就会留下"注意质量"这类废话。
2. **同名能力之间常常不是强弱关系，而是场景错配。** 例如 `paper-deweight` 与 `paper-polisher` 是互斥场景（学术语体去 AI 痕迹 vs Word 精修留痕报告），写进 `mutex` 而不是排成一二名；`survey`/`experimental` 类库文件格式差异（`.sav`、`.dta`、复杂抽样权重）决定方法选择，也属于这类。
3. **有些技能的核心能力外包给了第三方服务。** 在线绘图 API、外部生图、AI 检测服务、付费修复工具——发布版必须能离线独立跑，这类技能只能降级或弃用，并在卡里写明替代路径。
4. **全库没有的东西要如实说没有。** 没有专职 meta-analysis 技能（`metafor` 零命中，`stats.meta` 只能由 `ima-lit-meta-ppt` 支撑并标注自实现公式须交叉验证）；没有任何技能提供影响因子/审稿周期/录用率（写成机械门"此类数字出现次数 = 0"）；本插件也不做查重与 AIGC 检测（润色域写在交付说明里）。
5. **资产比正文更容易变成幻觉来源。** 有的技能正文让"运行 `scripts/xxx.py`"，而脚本因预算没随包收——v3 因此在账本与 `catalog.assets` 里显式写 `included:false`，并在 `research_kb_read` 时提示"该技能资产未收录，需回原文看步骤或按协议手工执行"。
